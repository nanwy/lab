## Spec

1. **[P2] 阅读页可缺省字段被笼统写为必填。** [05](issues/05-knowledge-file-reader.md)第 10 行把 document.title、rendered_html、target.anchor_id 后接“缺字段明确报错”。原 QWs 对标题使用 `--` 回退，对空正文清空内容，target 使用可选访问；没有定位目标时也不阻止显示正文。不能因此将无标题、空正文或无引用锚点一律升级为契约失败。应明确区分原 UI 允许的缺省状态、合法空内容和已确认必填结构错误；原 UI 容错不等于已验证后端字段可选性。证据：Unicode 13320916–13323400，尤其 13322052、13322535 附近。

2. **[P2] 共享项批量操作的已知门控仍留作未决事项。** [02](issues/02-personal-file-management.md)第 10 行要求“批量入口和共享选中项的实际行为补证后验收”，但当前 bundle 已能确认：个人列表选择框仅禁用 `id=".."`；共享文件可以选中；批量删除按钮根据选择数量启用。`is_shared_file` 禁用的是单项重命名、删除及分享。应把前端差异写清，不能推导统一的“共享项禁止选择或批删”。这不证明服务端允许删除共享文件，真实授权仍单独验证。证据：Unicode 12651550、12653453、12653940、12654047 和 12654280–12655580 附近。

3. **[P2] 单文件下载命名行为没有落票。** [01](issues/01-browse-and-download.md)第 10 行仅写“单文件下载”。原个人资料使用 jf，公开资料使用 $E，下载文件名分别按不同规则去除服务端标识；这属于用户拿到的文件行为。应增加两域命名验收，并对多点文件名等原算法缺陷单独决定、记录修正理由，不能无意统一为 URL 尾段或显示名。证据：jf @ Unicode 1800433、$E @ 1800602，个人调用 @ 12653851，公开调用位于 ujs @ 12656272 后续。

Spec 发现 3 项，最主要问题是 05 的笼统必填要求会缩小原页面容许的阅读状态。主流程没有整块漏票，下载命名是目前确认的具体行为遗漏。
